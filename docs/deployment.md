# Phase 3: Vercel + Render deployment

## Architecture and limitations

- Vercel serves the existing React 18 / Vite 6 / TypeScript SPA from `frontend`.
- Render runs the existing FastAPI API and Celery OCR worker in **one Docker web service**. Redis is a separate Render Key Value service. Deployments without Redis set `PROCESSING_MODE=sync` and run OCR inside the API process (see "Processing mode" below).
- The active development environment uses SQLite and local uploads. Production preserves those technologies, with SQLite at `/var/data/landrecords.db` and documents at `/var/data/uploads` on a 10 GB persistent disk.
- SQLite and uploads must survive deployments. Render's normal filesystem is ephemeral, and disks cannot be shared across services. That is why this configuration keeps API and worker together, with one API process, one OCR worker, and one service instance. Do not create a separate worker using local storage or scale this service horizontally.
- Disk-backed deployments have downtime. Schedule deployments after OCR finishes. A forced shutdown can interrupt a job; inspect queued/running/failed jobs after a restart. This preparation does not introduce durable job recovery or change OCR task semantics.
- `app.deploy` creates directories, enables SQLite WAL, creates missing tables, supervises API/worker processes, and exits if either child exits so Render can restart the service. Missing-table initialization is not a migration system: future schema changes need explicit migrations and backups.
- The existing PostgreSQL and MinIO/S3 adapters remain available. No data is migrated or copied automatically. Moving to independent API/worker services would require shared PostgreSQL and object storage, and a separate migration decision.

## Processing mode (Redis-free deployments)

- `PROCESSING_MODE=sync` makes the API run the identical document pipeline inside the request. No Celery worker is started and Redis is never contacted, so a deployment without a Key Value service no longer retries the broker until the request times out. Multilingual OCR, `structured_data`, `detected_language`, `warnings` and `raw_text` are produced by the same code path as the worker.
- `PROCESSING_MODE=celery` keeps the existing asynchronous behaviour: `app.deploy` starts the Celery worker and `/documents/{id}/process` dispatches the task.
- `PROCESSING_MODE=auto` (default) uses Celery unless the deployment is `APP_ENV=production` with no explicit `CELERY_BROKER_URL`/`CELERY_BROKER_URL_OVERRIDE`, in which case it processes synchronously.
- Synchronous processing occupies the web instance for the duration of OCR. Keep one instance, expect one document at a time, and leave `PROCESSING_TIMEOUT_SECONDS` at `300`. The frontend allows 5 minutes for the processing request and, if the response is cut short, opens the document page, which polls the real job status.

Optional existing settings: `JWT_ACCESS_TOKEN_EXPIRE_MINUTES`, `JWT_REFRESH_TOKEN_EXPIRE_DAYS`, `MAX_UPLOAD_SIZE_MB`, `ALLOWED_EXTENSIONS`, `LOG_LEVEL`, `LOG_FORMAT`. Production rejects default/short signing secrets, debug mode, wildcard origins, and relative SQLite/storage paths.

No cloud OCR/LLM credentials are required for the current Tesseract/EasyOCR and structured extraction workflow. `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `GOOGLE_VISION_CREDENTIALS_PATH`, `AZURE_COGNITIVE_ENDPOINT`, and `AZURE_COGNITIVE_KEY` are existing optional integration settings; leaving them blank does not enable those integrations.

If deliberately configuring the existing object-storage adapter, use `STORAGE_BACKEND=minio` or `s3` and `MINIO_ENDPOINT`, `MINIO_ACCESS_KEY`, `MINIO_SECRET_KEY`, `MINIO_BUCKET`, `MINIO_USE_SSL`. This adapter uses the MinIO SDK even for `s3`; the previously suggested `AWS_*` variables are not consumed by it. Use a private bucket and a TLS endpoint hostname without `https://`.

`DATABASE_URL` is accepted as an alias when `DATABASE_URL_OVERRIDE` is absent. The override takes precedence. Both API and worker derive their URLs from the same value; PostgreSQL provider URLs are normalized to asyncpg for the API. Do not paste the local `.env` into Render.

## OCR dependencies

The existing Dockerfile installs Tesseract with explicit English/Hindi data and the existing Marathi, Bengali, Gujarati, Punjabi, Tamil, Telugu, Kannada and Malayalam packs. It also installs Poppler, `libgl1` and GLib. Python dependencies include headless OpenCV, Pillow, PyMuPDF, pdf2image, pytesseract, EasyOCR and langdetect.

CPU-only PyTorch/torchvision wheels avoid CUDA dependencies. English and English/Hindi EasyOCR readers download their weights during image build into `/opt/easyocr`, so those models do not depend on a first-request download. Build failure to download models must be resolved before deployment. Other EasyOCR language combinations may still download weights at runtime.

The image needs network access during build to Debian, PyPI, the PyTorch wheel index and EasyOCR model hosting. Use Docker/Linux Python 3.11 for full dependency validation; the local Python 3.14 environment is not equivalent.

## Exact Vercel settings

| Setting | Value |
| --- | --- |
| Root directory | `frontend` |
| Framework preset | Vite |
| Install command | `npm ci` |
| Build command | `npm run build` |
| Output directory | `dist` |
| Environment variable | `VITE_API_URL=https://your-api.onrender.com` |

Set `VITE_API_URL` to the Render **origin**, without `/api/v1`. Both normal requests and token refresh append `/api/v1` themselves. Set it for each Vercel environment you use; environment changes require a new build/deployment. This variable is public and must never contain credentials. Vercel builds fail if it is missing or not a deployed HTTPS origin.

`frontend/vercel.json` rewrites SPA navigation to `index.html`, allowing direct visits and refreshes on `/documents/...`, `/login`, etc. API calls go directly to Render. Local development keeps the existing Vite proxy when `VITE_API_URL` is empty. Existing same-origin Docker frontend builds remain supported outside Vercel.

## Dashboard sequence and URLs

1. Complete the Git/data checks below and make the repository available to Render and Vercel. Create/import the Vercel project with `frontend` as its root; note its assigned stable production domain. It is fine to leave the first deployment pending until the backend URL exists.
2. Create the Render Blueprint. Enter that Vercel origin into `CORS_ORIGINS`. Review the resource plans/disk, then deploy. Wait for the Docker build, API and worker startup. Check `https://your-api.onrender.com/health` returns `{"status":"ok"}` and `/api/v1/health` reports `database: connected`.
3. In Vercel, enter the actual Render origin in `VITE_API_URL`, then deploy/redeploy. Confirm the actual Vercel production origin is in Render's `CORS_ORIGINS`; update Render if needed. Test login, refresh, upload, processing, extraction and browser route refreshes.

CORS accepts comma-separated **exact origins**, without paths. Local development defaults already allow `http://localhost:3000` and `http://localhost:5173`. Add those explicitly to Render only if a local frontend must use production. For previews, add each approved preview origin explicitly; do not allow every `*.vercel.app` domain. Custom frontend domains also need an explicit CORS entry.

## Data and Git checks before publishing

`backend/landrecords.db` and `frontend/tsconfig.tsbuildinfo` were already tracked. Ignore rules do not remove tracked files or erase Git history. No database contents were printed, modified, or deleted as part of deployment preparation.

Stop tracking them while retaining local copies:

```powershell
git rm --cached -- backend/landrecords.db frontend/tsconfig.tsbuildinfo
```

Review the repository's existing history and access before making it public. If the tracked database contains private records or credentials, removing it from the next commit is insufficient: restrict repository access and arrange history cleanup/credential rotation where applicable. This change does not rewrite history. A bounded scan found no recognizable API-key/private-key patterns in current tracked text; this is not a guarantee about database contents or all history.

The new Render disk starts empty. If existing records must be retained, schedule a separate controlled import of a consistent SQLite backup and its corresponding uploads, with processing stopped. Do not commit a database backup or upload documents to transfer them. Back up the database and uploads together regularly; a persistent disk is not a backup policy.
